# Agentic Ticket Support System

An asynchronous AI customer-support application built for the [CockroachDB × AWS Hackathon](https://cockroachdb-ai.devpost.com/). Customers submit tickets through a React application, while a TypeScript supervisor on AWS retrieves durable context and vector memory from CockroachDB, resolves known issues, or safely escalates the request.

CockroachDB is both the transactional system of record and the persistent memory layer. Ticket state, conversations, plans, tool results, FAQ articles, and embeddings remain available across stateless AWS Lambda invocations.

## Features

- Asynchronous ticket processing through Amazon SQS
- CockroachDB Cloud Managed MCP Server for application data and agent memory
- 384-dimensional FAQ embeddings generated by Hugging Face
- CockroachDB vector search over category-filtered resolutions
- Direct completion for a trusted FAQ match, with Strands/Groq agent fallback
- Persisted plans, bounded tool cycles, idempotent job claims, retries, and safe escalation
- Customer ticket tracking and an auto-refreshing admin dashboard
- Structured CloudWatch logs and AWS X-Ray tracing

## Architecture

```text
React + Vite frontend
        |
        v
Public Lambda Function URL (ticket/job API)
        |
        +---- CockroachDB Cloud Managed MCP Server
        |       tickets, conversations, jobs, plans, tool results
        |
        +---- Amazon SQS job queue ----> Supervisor Lambda
                                          |     |
                                          |     +---- Strands + Groq
                                          |
                                          +---- Hugging Face embedding
                                                    |
                                                    v
                                          CockroachDB vector search
                                          resolution_embeddings +
                                          resolution_articles
                                                    |
                                                    v
                                          Complete or escalate job

Failed deliveries (3 attempts) ----> DLQ ----> escalation Lambda
CloudWatch Logs + AWS X-Ray <------ all Lambdas
```

The CockroachDB database is external to the CDK stack. Lambdas access it through the authenticated CockroachDB Cloud Managed MCP Server rather than direct database connections. CDK provisions three Node.js 22 ARM64 Lambdas, the job queue, dead-letter queue, Function URL, log groups, and event-source mappings.

## Request and memory flow

1. `POST /tickets` creates a ticket, conversation, and queued job, then publishes a versioned SQS message.
2. The supervisor claims the job idempotently and loads its ticket context and conversation from CockroachDB.
3. The latest request is embedded using `sentence-transformers/all-MiniLM-L6-v2` and compared with vectors in `resolution_embeddings`; matching text comes from `resolution_articles`.
4. A category-matched result with L2 distance `<= 1` is trusted FAQ memory and completes the job without another model call.
5. Otherwise, the Strands supervisor uses Groq and an allowlist of typed domain tools. Context-first ordering, a persisted plan, and a maximum of three tool cycles are enforced outside the prompt.
6. The frontend polls until the job is `completed`, `escalated`, or `failed`.

This makes vector retrieval part of the deployed application rather than an offline demo. Successful retrieval emits `vector_memory_loaded`; direct FAQ completion emits `job_completed_from_vector_memory`.

## Prerequisites

- Node.js 22 or newer and npm
- AWS account, CLI credentials or SSO profile, and a bootstrapped CDK environment
- Existing CockroachDB Cloud cluster and database
- CockroachDB Cloud service-account API key with sufficient MCP access
- Groq API key
- Hugging Face token with Inference API access

## Configure the backend

Copy the configuration template and replace its example values. The resulting file is ignored by Git; do not commit credentials.

```powershell
Copy-Item Backend/infrastructure/.env.example Backend/infrastructure/.env
```

```dotenv
DEPLOYMENT_STAGE=development
COCKROACH_CLOUD_CLUSTER_ID=<cluster-uuid>
COCKROACH_CLOUD_MCP_API_KEY=<service-account-api-key>
COCKROACH_CLOUD_DATABASE=ticket_support
CORS_ALLOWED_ORIGIN=http://localhost:3000
GROQ_API_KEY=<groq-api-key>
HF_TOKEN=<hugging-face-token>
```

Optional settings include `GROQ_MODEL_ID` and `SUPERVISOR_RESERVED_CONCURRENCY`.

## Database and FAQ embeddings

Apply the application schema from the local workstation:

```powershell
cd Backend/app/SupervisorAgent
npm install
npm run db:migrate
```

The FAQ importer also expects this vector table in the configured database:

```sql
CREATE TABLE IF NOT EXISTS public.resolution_embeddings (
  resolution_id UUID PRIMARY KEY REFERENCES public.resolution_articles (resolution_id) ON DELETE CASCADE,
  embedding VECTOR(384) NOT NULL,
  embedding_model STRING NOT NULL,
  content_hash STRING NOT NULL,
  embedded_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE VECTOR INDEX IF NOT EXISTS resolution_embeddings_idx
ON public.resolution_embeddings (embedding);
```

Preview the FAQ parser, generate embeddings, and verify the schema and runtime permissions:

```powershell
npm run db:embed-faq:dry-run
npm run db:embed-faq
npm run db:check
```

The source content is in `Backend/database/faq-resolutions.md`. Keep the model and vector dimension consistent because vectors from different models are not comparable.

## Deploy the backend

```powershell
cd Backend/infrastructure
aws sso login
npx cdk bootstrap --termination-protection
npm run diff
npm run deploy
```

The deployment preflight builds the code, checks the database schema and MCP permissions, and verifies Groq access before changing AWS. Record the `JobApiUrl` CloudFormation output.

After changing the supervisor or embedding flow, redeploy and submit a **new** ticket. Terminal jobs are idempotent and are not automatically rerun.

## Run the frontend

```powershell
cd Frontend
Copy-Item .env.example .env
```

Set the deployed Function URL in `Frontend/.env`:

```dotenv
VITE_API_BASE_URL=https://<function-id>.lambda-url.us-east-1.on.aws
```

Then start Vite:

```powershell
npm run dev
```

Open `http://localhost:3000`. If the browser origin changes, update `CORS_ALLOWED_ORIGIN` and redeploy the backend.

## API

| Method | Route | Description |
| --- | --- | --- |
| `POST` | `/tickets` | Create a ticket, conversation, and asynchronous job |
| `POST` | `/jobs` | Queue a job for an existing ticket |
| `GET` | `/jobs/{jobId}` | Read job progress and terminal response |
| `GET` | `/tickets/{ticketId}` | Retrieve a ticket and its latest job |
| `GET` | `/tickets` | List recent tickets for the demo admin dashboard |

## Verify the deployed vector flow

Submit a new ticket close to an FAQ, such as `I requested a new login link, but I still cannot get into my profile.` Poll its job until terminal, then inspect the supervisor log group:

```powershell
aws logs tail <SupervisorLogGroupName> --region us-east-1 --since 10m --follow
```

A successful FAQ-memory path emits:

```text
job_processing_started
vector_memory_loaded
job_completed_from_vector_memory
```

If the final event is `job_escalated` or `supervisor_job_failed`, use its `jobId`, `ticketId`, and `conversationId` to correlate CloudWatch with CockroachDB. A failed job is retried up to three times before the DLQ handler escalates it.

## Security and production notes

This repository is configured as a hackathon demonstration:

- The Lambda Function URL and admin ticket-list endpoint are public and unauthenticated.
- CORS controls browser origins; it is not authorization.
- API keys are injected from a local ignored file. Production should use AWS Secrets Manager.
- Add authentication, per-customer authorization, rate limiting, and PII controls before using real support data.
- The current CDK stack does not host the static frontend.
